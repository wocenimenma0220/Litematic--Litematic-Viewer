# ScalableLux 0.2.1 对投影预览的光照优化评估

评估日期：2026-10-14。后续版本继续使用 **1.0.17.x**；评估时发布版为 **1.0.17.1**。

结论：很有借鉴价值，重点是首次光照计算、光照常驻数据和遮光规则。它计算方块光与天空光，
不负责平滑阴影、材质、几何 LOD 或 GPU 绘制，因此不能直接解决所有预览问题。
原始评估完成源码阅读、独立算法原型与正确性验证。后续运行时改动见下方“1.0.17.2 落地记录”；第 3 节数字仍是原型实验，不是新发布版整体性能。

## 1. 实际源码如何工作

### 光源收集与天空光初始化

`BlockStarLightEngine.getSources()` 跳过空区块，也先检查区块调色板是否包含发光方块；只有可能有光源时才扫描 4096 个位置。
`SkyStarLightEngine.lightChunk()` 从最高的非空区块向下初始化天空光，处理空区块的光照延伸，然后检查相邻区块边界。
`tryPropagateSkylight()` 单独处理满级天空光向下不衰减，以及源面和目标面是否挡光。

定位：`ScalableLux-0.2.1/src/main/java/ca/spottedleaf/starlight/common/light/BlockStarLightEngine.java:199`、
`SkyStarLightEngine.java:451`、`SkyStarLightEngine.java:605`。

### 有方向信息的传播队列

`StarLightEngine` 的 `long[]` 队列将局部坐标、光照等级、六方向位集和状态标记编码进一个整数。
传播到邻居后通常排除刚来的反方向；必要时检查队列中记载的亮度是否过期。
增加和降低亮度分别处理，动态方块变化会先撤销旧影响，再重新传播剩余光源。

其中对我们的直接价值是判断顺序：**先读邻居光照，已经足够亮就跳过，再读取方块、遮光值和形状**。
不是每次都进入昂贵的方块查询与形状判断。空白天空也应尽量只设置结果，不送进无效传播队列。

定位：`StarLightEngine.java:1056`、`:1119`、`:1162`、`:1217`。

### 小范围数组缓存

每次处理时，先把邻域的方块区块、光照区块和空区块信息放入数组缓存；X/Z 为 5×5，另覆盖需要的高度范围。
热循环通过区块索引和区块内索引访问，减少哈希表查找、临时坐标对象和重复取得区块的操作。

定位：`StarLightEngine.java:107`、`:149`、`:218`、`:288`。

### 四位存储、延迟分配与读写快照

一个 16³ 区块，每个光照通道使用 2048 字节：一个字节保存两个 0–15 的亮度。
`SWMRNibbleArray` 区分不存在、未初始化、已初始化和隐藏状态，零值数据可不分配数组。
更新缓冲与可见缓冲分开，在发布时才更新读者看到的数据；工作数组有线程局部复用池。

这份源码并没有为任意“统一亮度”提供通用常量页；我们的实验进一步尝试了统一值页，包括全 15 天空光。
因此实验中的常量页节省量是适合离线渲染的延伸方案，不能当作 ScalableLux 本身的实测数据。

定位：`SWMRNibbleArray.java:20`、`:25`、`:28`、`:335`、`:386`、`:429`。

### 安全的并行任务

`StarLightInterface.schedulePropagation0()` 以区块为任务，向调度器申请半径 2 的 X/Z 区域锁，即 5×5 区块。
重叠任务互斥，足够远的任务可同时执行；每个任务借用独立传播器，而非让多个线程同时修改同一份引擎缓存。

定位：`StarLightInterface.java:581`、`SchedulingUtil.java:10`、`GlobalExecutors.java:11`。

## 2. 与当前实现的对应关系

| 项目 | 当前投影预览 | 可借鉴的改进 |
| --- | --- | --- |
| 传播规则 | 从光源向外增加光照，已有 FIFO 与待处理位集 | 基础方向相同，不需要整套推倒重做 |
| 无效查询 | 稠密路径先读取目标方块，再判断光照是否需要提高 | 改为先检查邻格亮度，跳过无效方块查询 |
| 初始队列 | 稠密路径把所有亮度大于 1 的格子入队 | 只入队可能提高邻居的格子；稀疏路径已经部分实现 |
| 队列内存 | 稠密路径每通道预留 `int[整个体积]` | 随实际传播前沿增长的环形队列 |
| 光照存储 | 天空光、方块光各一字节；稀疏区块也立即分配两组 4096 字节 | 四位区块页，结合零值、统一值和延迟分配 |
| 邻区访问 | 稀疏传播已有六邻区缓存；采样入口仍查区块哈希表 | 为网格区块绑定只读邻域采样缓存 |
| 遮光 | 主要通过模型形状与贴图透明度推导 | 分离渲染遮挡、光照衰减和按面遮光规则 |
| 并行 | 光照先整体完成，再导出几何 | 邻域任务锁、边界收敛检查、稳定快照后才发布几何 |

当前对应位置：`LightVolume.java:137`、`SparseLightVolume.java:16`、`:122`、`:152`，以及
`SmoothLighting.java:37`。稀疏分块、邻居缓存、只增加亮度和跳过无效种子等思想已经部分存在，
应补齐剩余热路径，而不是为了接入模组再维护两套重复系统。

## 3. 独立原型对照实验

入口：`tools/verify/ScalableLuxLightingStudy.java`。
结果：`tools/verify/lod-output/scalablelux-study/result.json`。

原型保持现有遮光、衰减和光源规则，只实验三项：目标亮度提前判断、初始种子筛选、动态环形队列。
先比较两种实验路径的每个天空光和方块光值，再与应用当前 `LightVolume` 逐格对照。
另外实际编码四位页/统一值页，并逐格解码验证无损。

Java 25.0.4.1；每组预热 2 次、各测 5 次，交替执行两种路径，取中位数。两边均启用工作计数。
下表记录最后一次完整运行；本机另一次运行的真实样本结果为 165.9 → 94.7 ms，说明绝对耗时会波动。

| 样本 | 维度 | 基线中位数 | 实验中位数 | 速度比 |
| --- | --- | --- | --- | --- |
| 完全开放天空 | 96×64×96 | 47.8 ms | 27.5 ms | 1.74× |
| 屋顶与多个光源 | 96×64×96 | 81.5 ms | 57.3 ms | 1.42× |
| 不完整边缘区块 | 48×33×35 | 37.5 ms | 22.1 ms | 1.70× |
| 《璃月港》裁切样本 | 96×64×96 | 195.2 ms | 113.7 ms | 1.72× |

四组样本共 **1,824,912 个格子**，两个通道均与当前生产算法一致。
真实样本来自 `Unnamed` 区域内起点 `(541, 0, 427)`，含 260,589 个非空气方块，
直接读取压缩方块容器；裁切范围作为独立光照场计算，不代表完整璃月港的光照边界或整图耗时。

真实样本中，可计数的方块查询从 **5,413,461 次降至 2,092,591 次，约减少 61.3%**；
初始队列条目从 190,428 降至 33,020。单通道传播队列数组容量从 **2.25 MiB 降至 0.25 MiB**。

四位编码及统一页实验中，该样本两个光照通道的数据载荷从 **1,179,648 字节降至 342,016 字节，约减少 71.0%**。
仅使用四位页、不使用统一页时为 589,824 字节。这些数字不包含对象、页索引、方块数据和传播队列，
也没有证明构建峰值内存降低同样比例；实验仍保留原始数组供比较。
不完整边缘区块会有填充开销，不能把“四位节省一半”直接套到所有稠密体积。

以上是适配思路的离线原型测量，不是运行 ScalableLux 模组所得，也不是软件总启动时间、GPU 帧率或总内存的提升比例。
几何生成与平滑光照采样还要单独测量，尤其需要核对四位解码对高频网格采样的代价。

## 4. 已复现的一项现有正确性问题

原版 `26.3-client-src/net/minecraft/world/level/block/TintedGlassBlock.java:15` 明确返回光照衰减 15，
并阻止天空光向下传播。遮光玻璃可以让玩家看过去，但必须挡住光。

当前 `BlockShape.occludes()` 将模型透明度用于渲染遮挡；`LightVolume.skyOpacity()` 又依赖这个结果，
因而将遮光玻璃视作透光。光照语义与贴图透明度混在一起。

已用当前生产算法构造并测量两个封闭场景：

- 火把照向完全封闭的遮光玻璃隔墙，墙后的方块光测得 **11**，按原版衰减应为 **0**。
- 石墙房间使用完整遮光玻璃屋顶，屋顶下天空光测得 **15**，按原版规则应为 **0**。

这是已确认的问题。本轮记录了复现数据，发布版尚未修正。
台阶和半砖还需要源面、目标面的遮光形状比较；目前只是确定了缺失的机制，没有把它们全部判定为已复现故障。
ScalableLux 直接使用 Minecraft 的衰减和形状接口；我们的离线引擎需要独立补充语义，不能单靠换传播队列解决。

## 5. 建议落地顺序

1. **遮光规则与传播热路径。** 分离光照衰减和渲染透明度，先修复遮光玻璃；再接入提前亮度检查、种子筛选和动态队列。
   性能优化应保持逐格结果一致，语义修复另外用原版预期验证，避免用“与旧算法一致”掩盖原有漏光。
2. **压缩光照区块页。** 保留现有 `LightSampler` 接口，区分零值、统一值、混合四位数据；直接使用延迟分配才能改善构建峰值。
   仅在计算后压缩，只能主要减少常驻内存。不要在未测量前放宽大投影的分配保护。
3. **只读邻域缓存。** 网格生成时绑定附近光照页，减少 `cellLight()` 的区块哈希查询；与紧凑页一起测量采样吞吐。
4. **光照与几何的分块流水线。** 确保邻域光照边界稳定后再发布网格，使用版本号避免旧结果覆盖新结果。
   并行化再引入区域任务锁；不可仅将当前全局循环放入线程池。

当前投影不支持编辑方块，光照结果计算后只读，因此暂不需要整套动态减光队列与单写多读更新协议。
这些机制适合将来支持动态方块或构建中发布光照时再引入。

本地模组依赖 Fabric、Minecraft 运行时和 FlowSched；当前 FlowSched 子目录为空。
此次没有编译或加载模组。直接复用源码还需保留其 LGPL-3.0-only 来源与许可，
当前实验为独立实现，没有复制 ScalableLux 的传播器或存储类。

另外，附带 `TECHNICAL_DETAILS.md` 开头已声明旧版性能对比不适用于较新的原版引擎；
历史图表不作为本项目性能结论，以上建议以当前源码与本机独立实验为依据。

## 6. 1.0.17.2 落地记录（2026-10-14）

已把亮度提前判断、初始种子筛选和动态环形队列接入真实光照稠密路径；种子收集只读取一次目标方块。
稀疏路径同样先判断亮度，再读取方块。其两通道由 4096 字节数组改为零值/统一值/混合四位页：
混合页 2048 字节，全零方块光不分配载荷，全亮天空以常量开始，计算完成后回收统一值页的载荷。
不完整边缘的填充格保持零，避免它们成为额外天空光源。稠密通道暂时仍为 byte 数组，分配保护未放宽。

光照采样保存当前区块并复用其六邻区引用，按线程保留采样缓存；对角跨块仍通过索引查找。
这是常用邻域采样的缓存，没有声称已经实现整个只读 3×3×3 绑定或并行流水线。

真实光照的遮光玻璃衰减独立于贴图透明度，阻断天空光和方块光；含水方块及树叶也使用独立衰减。
评估中的两个封闭复现场景现在均测得 0。旧明亮显示模式仍保留其原有外观。

验证入口：CompactLightRegression、RenderingControlsRegression、rendering-controls-ui.cjs。
78,540 格跨不完整区块的稠密、紧凑、稀疏通道逐格一致；遮光玻璃与独立传播原型对照也通过。
另检查关闭光照时不创建光照体积、预览及导出缓存正确区分设置、PNG/GIF 与预览设置一致。
原型结果重新运行时使用更新后的衰减规则，因而不再作为第 3 节历史结果的原样复跑。

尚未落地：稠密光照的统一页存储、台阶/半砖的双面遮光形状、光照与几何流水线和区域锁并行。
此次没有把原型速度比当作软件整体加载速度、GPU 帧率或完整投影内存节省比例。

## 7. 1.0.17.3 更新（2026-10-15）

稠密路径也采用 LightGrid 的延迟统一页 / 四位页；为每个网格区块绑定只读邻域，并在稳定光照与固定图集后用有界队列重叠构建与输出。
已与 1.0.17.2 发布类逐格对照并测量计算、采样与粗略堆峰值。真实裁切载荷减少约 64.9%，该次计算耗时增加约 11.3%；
因此这项改动是内存取舍，不能称作全面提速。完整方法与结果见 [LiteTool渲染与大投影加载评估.md](LiteTool渲染与大投影加载评估.md)。
