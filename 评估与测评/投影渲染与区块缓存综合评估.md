# 投影渲染与区块缓存综合评估：LiteTool、Voxy 与本项目

评估日期：2026-10-15。本文把此前 LiteTool 实测与本次 Voxy 源码分析放在一起，给出本项目可实施的改造顺序。
第 1–7 节保留 1.0.17.4 时的评估基线；1.0.17.5 已按建议实施的结果、实测和剩余边界见第 8 节。1.0.17.6 的超大原始数据读取与退出清理见第 9 节，1.0.17.7 的完整区块渐进发布见第 10 节，1.0.17.9 的紧凑格式、真实 32 格构建和光照结果见第 11 节。

## 结论

两者解决的是不同环节：LiteTool 的样本主要靠降低首屏准备量，先显示粗网格；Voxy 则把体素数据持久化，
按需载入内存并生成各层级几何，再根据可见性保留或回收 GPU 数据。应组合这些思路，而不是把“区块缓存”当成一个开关。

对本项目，优先级最高的是**跨重启复用已生成的场景文件和图集**，其次是**先发布总览、再补细节**。
评估基线的 GPU 档位缓存已经能复用漫游与缩放中暂时不用的几何，当时缺少可靠的磁盘缓存命中和冷启动渐进发布。

本次还确认一个容易误判的地方：Voxy 源码声明了 4 GiB 的 CPU 几何缓存，但这份源码没有对应写入调用，
移除几何的路径直接释放 GPU 区块。不能把这项声明当作已经生效的“大容量网格缓存”，更不能据此估算本项目收益。

## 2. 同样叫“缓存”，实际保存的内容不同

| 环节 | LiteTool 本次样本 | Voxy 本地源码 | 本项目当前路径 |
| --- | --- | --- | --- |
| 首次准备 | 大图跳过 LOD0 与完整图集，先生成 LOD1–3 单色网格 | 导入体素及各级汇总，再按层级需求构建网格；没有本机时间数据 | 先稳定光照、固定图集，生成完整精度及四档 LOD 文件 |
| 磁盘持久化 | 未从该 EXE 的现有证据确认具体区块缓存格式 | 调色板体素序列化 → Zstd level 1 → RocksDB，另存全局 ID 映射 | 有随机访问 LMESH5 文件，但没有可验证的跨会话场景缓存目录 |
| CPU 内存 | 确认可分批构建；具体缓存和淘汰策略不能从模块名推断 | 活跃体素区块 + 闲置区块 LRU + 数组复用池 | 保留当前解析及构建状态；没有 Voxy 这种独立体素数据库 |
| CPU 几何 | 未确认 | 有 `GeometryCache` 类及读取接口，本地源码未接通写入 | 没有独立 CPU 几何二级缓存；几何页可从已生成文件重读 |
| GPU 工作集 | 按距离选 LOD、分批上传；本次最多 16 区块一批 | 大几何缓冲、层级节点、可见帧记录及计算着色器清理 | `residents`、总览保底与闲置档位缓存，共用可配置几何预算 |
| 区块关系 | 日志记录 32 格分块 | 每个 `WorldSection` 是 32³ 体素，层级 0–4 的覆盖尺度扩大 | 16³ 所有权区块；每块内有四档简化，不等同于 Voxy 的大范围父区块 |

Voxy 的磁盘里主要保存可重新生成网格的体素数据，不能把“有磁盘缓存”理解成“下次完全不用构建网格”。
本项目的投影通常是不可变快照，已经生成的 LMESH5 更适合作为第一阶段的持久缓存，暂时不必先引入完整世界数据库。

## 3. Voxy 的有效缓存链路

### 3.1 区块标识与分级体素

`WorldEngine.getWorldSectionId` 把层级和坐标编码进一个 64 位键。`MAX_LOD_LAYER = 4`，
每个层级的 `WorldSection` 都容纳 32×32×32 个体素；层级越高，一个体素代表的范围越大。
`Mapper` 在体素值中保存方块状态编号、生物群系编号与光照，并将编号映射单独保存到存储后端。

`WorldUpdater` 从低层更新到父层，传播子块存在位；没有状态或空置变化时停止向上更新。
这让远处可直接读取已经汇总的父层数据，避免每次远景显示都重新遍历全部细格。
它不是单纯把完整精度三角形等比例减少，而是另有体素层级和模型表示。

[WorldUpdater](/D:/litematic-display/voxy-dev/src/main/java/me/cortex/voxy/common/world/WorldUpdater.java:13)、

### 3.2 活跃区块与闲置区块 LRU

`ActiveSectionTracker` 使用 64 个分片映射和分片锁，保存正在使用或正在加载的区块。
同一键首次请求创建占位对象，由一个加载者读取；其他请求等待该对象发布，避免重复从磁盘读取同一区块。
它的等待使用原子字段、内存屏障与自旋/yield，并不是可取消的异步 Future 接口。

区块通过引用计数保护。最后一个使用者释放后，已清理保存状态的区块进入第二级闲置缓存；再次访问从闲置缓存取回，
超过容量则移除最早闲置的条目并释放其数组。待保存的脏区块先进入保存流程，不能直接当成普通闲置对象释放。

默认闲置缓存为 1024 块；最大堆接近 4 GiB 时改为 2048 块。每块原始 `long[32768]` 的载荷为 256 KiB，
对应 256/512 MiB 的闲置载荷上限量级，尚未计入活跃块和对象开销。
`WorldSection` 另有最多 400 个数组的复用池，其载荷可达约 100 MiB；不能把“释放对象”简单等同于立即归还全部内存。

来源：[ActiveSectionTracker](/D:/litematic-display/voxy-dev/src/main/java/me/cortex/voxy/common/world/ActiveSectionTracker.java:54)、
[WorldSection](/D:/litematic-display/voxy-dev/src/main/java/me/cortex/voxy/common/world/WorldSection.java:39)。

### 3.3 磁盘序列化、压缩和数据库

默认链路由 `StorageConfigUtil.createDefaultSerializer` 实际组装：

```text
WorldSection 的 32³ 体素
  → SaveLoadSystem3：局部调色板 + 16 位索引 + 区块键与子块标志
  → CompressionStorageAdaptor：Zstd level 1
  → RocksDB 的 world_sections 列族
```

`SaveLoadSystem3` 序列化前的尺寸为 `16 + 32768×2 + 8×不同体素值数量` 字节。
例如统一值区块在 Zstd 之前仍是 65,560 字节；真正压缩重复索引的是后续压缩器。
这里的体素值含光照和群系，局部调色板的不同值数量不能直接当作方块种类数量。
类里虽有 `lin2z/z2lin` 帮助函数，本次实际 `serialize` 按 `data` 的线性顺序遍历，不能把它描述成已使用 Morton 顺序编码。

RocksDB 将 `world_sections` 和 `id_mappings` 分开。区块列族关闭数据库自身压缩，避免重复压缩已被 Zstd 包装的数据；
另配置 128 MiB 的 HyperClock 块缓存、Bloom 过滤和点查找索引。该块缓存是数据库层缓存，与 Java 的区块 LRU 不同。
按世界标识和基础保存路径分隔数据库；数据编号映射需与该库保持一致。

来源：[默认存储配置](/D:/litematic-display/voxy-dev/src/main/java/me/cortex/voxy/common/StorageConfigUtil.java:54)、
[序列化](/D:/litematic-display/voxy-dev/src/main/java/me/cortex/voxy/common/world/SaveLoadSystem3.java:40)、
[RocksDB 后端](/D:/litematic-display/voxy-dev/src/main/java/me/cortex/voxy/common/config/storage/rocksdb/RocksDBStorageBackend.java:44)。

### 3.4 脏数据保存与任务复用

`SectionSavingService` 用保存队列状态避免同一区块重复排队，保留引用直到写出完成。
队列超过 5000 项时，允许阻塞的提交者会协助处理积压；这是带协作处理的软阈值，不能写成绝不会超过 5000 的硬容量队列。
关闭时等待保存任务并处理剩余项，再刷新存储。

网格任务另用键到任务的映射合并排队请求，并按层级和重试状态排序，较粗的层级可以较早得到处理。
缺失模型时请求模型烘焙并重排；最多暂持 1000 个区块引用。正在执行的任务与后续更新仍有各自生命周期，
不应夸大为任何时刻都绝无重复计算或有完整取消协议。

来源：[SectionSavingService](/D:/litematic-display/voxy-dev/src/main/java/me/cortex/voxy/common/world/service/SectionSavingService.java:44)、
[RenderGenerationService](/D:/litematic-display/voxy-dev/src/main/java/me/cortex/voxy/client/core/rendering/building/RenderGenerationService.java:279)。

### 3.5 GPU 工作集与未接通的 CPU 几何缓存

GPU 几何使用共享缓冲和节点元数据。`NodeCleaner` 根据节点的可见帧信息，使用计算着色器挑出清理候选，
每批最多输出 256 个；当前实际触发条件是剩余几何容量小于 256,000,000 字节，代码里“75%”的另一路径被 `if (false)` 禁用。
因此不能用注释中的旧百分比解释当前行为。

`AsyncNodeManager` 的确构造 `new GeometryCache(1L << 32)`，初次请求会尝试 `remove(pos)`，
世界更新会 `clear(section.key)`，销毁时会 `free()`。
但扫描整个 `src/main/java`，没有 `geometryCache.put(...)` 调用；`NodeManager.removeGeometryCached` 目前直接调用 `removeSection(id)`。
虽然另有下载几何接口，当前移除调用没有把下载结果送进此缓存。结论是：**缓存容量和命中接口存在，写入链路在这份源码中没有接通。**

Voxy 的普通几何记录可以压到每四边形 8 字节，由渲染侧结合模型数据解释。
本项目 LMESH5 是每顶点 20 字节、每四边形 80 字节，支持任意顶点、UV、颜色、流体及特殊几何。
这个差异值得研究，但并不等价于全场景显存可无损缩小十倍；模型库、索引、节点和特殊模型的成本及表示能力都要一起比较。

### 3.6 不能直接照搬的部分

这份版本的序列化元数据没有完整写入格式版本和内容校验的实现；损坏区块的处理会删除存储条目并回退为空气。
压缩器也留有错误检查的待办。对我们的投影缓存，应验证长度、格式、源文件指纹和校验值，失败就从原始投影重建，
避免把失败缓存显示成投影缺块。

Voxy 集成 Minecraft、Fabric、Sodium、LWJGL、原生压缩/数据库及桌面 OpenGL。
本项目是离线 Java 引擎与 Electron WebGL，不能直接使用其计算着色器、缓冲管理或 Minecraft 的区块/模型对象。

## 4. 和 LiteTool 实测放在一起看

以下数字来自前轮相同机器的顺序测试，不是 Voxy 的运行结果，也没有复测成 1.0.17.4 的性能承诺。
大投影《璃月港》有 18,948,750 个非空气方块，范围 1178×253×950。

| --- | --- | --- |
| 读取投影 | 1.627 秒，仅读取运行 1.868 秒 | 1.605 秒 |
| 首个可见区块 | 3.520 秒 | 没有测 UI 首屏；当前等待完整分块文件 |
| 可渲染准备 | 3.798 秒 | 分块与图集文件准备 62.293 秒，不含 UI 传输与 GPU 上传 |
| 准备质量 | 跳过 LOD0 和完整图集，LOD1–3 单色网格 | 完整材质、稳定光照、透明排序、特殊几何及四档 LOD |
| 完整网格文件 | 本次不适用 | 1,168,519,764 字节 |
| 资源初始化 | 范围与本项目不同，不做等值对照 | 冷资源会话 23.365 秒，后续复用 |

小投影完整材质模式：LiteTool 强制 `--no-lod` 首图约 2.055 秒；本项目复用资源后的完整场景与文件准备约 2.316 秒。
两者资源和特殊模型支持不同，未做同相机逐像素比较。LiteTool 在本地 26.3 材质上还报告部分悬挂告示牌和贴图回退问题。

由此得到的项目判断：压缩投影读取不是这个大样本的主要差距，资源初始化、完整网格生成量及发布时机更关键。
Voxy 的持久化能帮助“再次访问”，LiteTool 的粗档先行能帮助“第一次看到”；只增加内存 LRU 无法同时解决这两个问题。

前轮光照页压缩还测得真实裁切载荷下降约 64.9%，计算耗时增加约 11.3%。它是内存取舍，不能当成加载全面提速的证据。

## 5. 本项目已有的缓存与真正缺口

当前 `lod-stream.js` 已保存正在显示的档位、总览保底和暂时不用的档位。缩放或返回旧位置时，若该档位仍在预算内，
直接复用已上传的 GPU 缓冲；预算不足才淘汰。默认几何预算 256 MiB，用户可调整，临时空间也计入预算。
因此不能建议“先加一个 LRU”而忽略现有机制，也不能把现有档位缓存错误归类为只缓存压缩文件字节的 CPU 缓存。

现有 LMESH5 支持页偏移和随机读取，每页最多 8192 个四边形。它适合按需传输；但完整目录在文件尾，
必须等构建完成才交给界面。场景复用依据当前引擎内的键和索引对象，缺少重启后可验证并恢复的完整目录与资源指纹。

## 6. 建议的改造顺序

### 第一阶段：持久化当前完整场景，先改善再次打开

复用现有 LMESH5 与图集，增加持久缓存清单和可恢复索引；完成后再发布清单，未完成任务只留临时文件。
键至少包含投影内容指纹、引擎/格式版本、资源包内容与顺序、光照模式、生成图集规则、已解析的玩家皮肤和其他动态资源指纹。
文件名、修改时间和长度可以用于快速检查，但不能作为唯一正确性依据。

打开时验证清单、文件长度与校验值，命中则直接恢复索引和图集，跳过场景重建；失败则从原投影重建。
缓存按实际磁盘字节配置限额，清理未使用的旧条目，不能让所有历史投影无限占用磁盘。
本阶段先服务 GPU 预览；点选、皮肤/实体报告和 PNG/GIF 导出需分别验证，不能假设它们自然复用 GPU 文件。

初版建议使用不可变场景文件加清单，不急于引入 RocksDB：本项目主要是静态投影，已有约 1.17 GB 的完整分块样本，
首要收益是可靠复用，而不是先复制一个面向持续更新世界的数据库栈。

### 第二阶段：粗档优先发布，改善首次打开

借鉴 LiteTool 的首屏策略和 Voxy 的按需层级任务，先显示明确标识的总览，再补视距内的完整材质。
这需要可增量发布的目录或独立页文件，旧 LMESH5 不能简单“写一半就读取”。
每个区块/档位只保留一个排队任务；位置或投影改变时用任务版本丢弃旧结果，清理暂时资源，保持总览可用。
光照和图集有稳定边界后才发布依赖它们的网格，避免边界明暗和 UV 在补细节时错乱。

### 第三阶段：独立压缩页与分层预算

对每页独立压缩，保留偏移、压缩长度、解压长度、校验值和格式版本，避免每次读取整场景解压。
现有最大页原始顶点约 640 KiB，可作为实测起点；对照 JDK 自带压缩与其他方案的读取、解压、占用和打包成本，
再决定是否增加原生压缩依赖。不能在没有本机结果时承诺压缩率或毫秒收益。

把磁盘缓存、可选 CPU 页缓存、GPU 几何和读取临时区分开统计和限额；继续复用现有 GPU 档位缓存，
避免额外保留同一份原始数据、解压数据及 GPU 副本而没有统一预算。只有回访统计证明有收益，再增加 CPU 二级缓存。

### 第四阶段：评估紧凑面与更大的层级单元

对规则轴对齐方块尝试紧凑面记录，保留流体、活板门、实体、头颅和复杂透明几何的通用顶点路径。
分别测试 16/32 格构建和缓存单元，观察吞吐、回访命中、峰值、剔除精度和交界正确性。
Voxy 的 8 字节面与大范围父层级属于表示和渲染架构调整，不能包装成一项低风险的缓存参数修改。

## 7. 验收方法

| 场景 | 应记录或确认 |
| --- | --- |
| 首次打开、再次打开、重启后再次打开 | 分别记录读取、资源初始化、光照、网格、读盘、GPU 上传和首个可见帧；记录实际命中层级 |

### 8.1 缓存正确性与取消

缓存键采用原投影字节、引擎编译内容、材质包内容及顺序、光照开关、已解析皮肤的实际像素和回退状态。
同路径、同大小、同修改时间但内容不同的投影或贴图，会失效；导入包优先级不同也会失效。
缓存清单检查网格和图集的长度及 SHA-256，之后验证目录格式、边界、页范围和总面数。失败从原投影重建，未完成束不发布。

真实新 JVM 检查的完整网格构建次数为首次 **1**、同进程再次 **0**、重启后 **0**，网格与图集文件保持一致。
同时验证点选、PNG/GIF、损坏后相同重建、光照失效、原文件/资源包同时间同长度的修改。
独立策略测试覆盖实际字节 LRU、当前文件保护、失败发布、关闭保留后的临时文件回收、禁止越界删除、包顺序与不可变皮肤快照。

任务状态和取消不占用构建监视器。扫描、光照传播、队列等待和区块边界检查中断；停止时等待生产者释放自身缓存后再切换资源。
UI 同时检查文件打开顺序、预览任务编号和 GPU 上传代数，防止迟到结果覆盖新投影。

证据：`tools/verify/SceneCacheRegression.java`、`CachePolicyRegression.java`、`voxy-cache-ui.cjs`；结果在 `tools/verify/cache-output`。

### 8.3 独立压缩与预算取舍

每个普通页最多 8192 面，原始顶点 640 KiB；透明 BSP 页原始上限 16 MiB。
主进程限制单路读取/解压，限制解压输出，检查精确长度与 CRC，读取临时预算为 80 MiB；页描述不能自行指定额外文件路径。
磁盘限额默认 4096 MiB，允许 0 或 256–131072 MiB；只对已完成保留束执行 LRU，当前使用束和本次临时构建另说明。
几何工作集继续使用原 GPU LRU，默认 256 MiB；没有再缓存一份解压页面。目录、投影、光照、图集、Java/Electron 开销分别看待。

额外抽取 96 页、4,342,080 原始字节，用本机 Python zlib 对比等级；这是独立验证，不冒充 JDK 或 Voxy 的运行结果：

| 等级 | 压缩字节 | 压缩耗时 | 解压耗时 |
| --- | --- | --- | --- |
| 1 | 953,640 | 34.4 ms | 11.7 ms |
| 3 | 889,623 | 69.7 ms | 9.4 ms |
| 6 | 726,816 | 153.1 ms | 8.7 ms |

本轮选择无额外依赖的 JDK level 1，避免高等级继续拖延首次完整构建。未取得 Zstd/LZ4 的同机运行结果，不声称它们更快或更慢，暂不增加原生库。
读取测试还覆盖错误 CRC、损坏载荷、短页、错误算法、超限解压、旧权限与其他窗口访问；缓存文件损坏在下次打开时重建。

### 8.4 紧凑面与 16/32 格单元实验

独立实验按完整档的规则层每 125 面取一面，共 50,139 面；其中 46,539 面可以无损编码为 **40 字节**。
记录含区块内坐标、轴、四角排列、原始 UV 和四角 RGBA，逐条解码并按全部 80 字节比较；其余面保留通用记录。
在这个规则层样本中，候选比例约 92.82%，混合记录从 4,011,120 降至 2,149,560 字节。
这不是全场景候选比例，也不是已测 GPU 显存收益；透明流体、特殊几何、非单位矩形与模型表成本仍要单独处理。

32 格实验把现有 16 格区块按 2×2×2 分组，使用 A→B→A 的 96 格邻域与 LRU 模拟。
分组数由 11,206 减少为 2,044，但同一路径读取的压缩完整档由 **9,873,113** 增至 **14,281,311** 字节，约多 44.7%；
合计多触及 394 个邻域外区块。32 与 256 MiB 模拟预算下均没有淘汰，所以该路线本身不能证明更大缓存组能减少抖动。

结论是本轮继续采用 16 格生产/缓存单元。真实 32 格烘焙吞吐、剔除、光照交界、峰值和 GPU 紧凑解码仍需后续专门实验，
不因为 Voxy 使用 32³ 和 8 字节面，就直接替换本项目所有通用模型。

证据与复现：`tools/verify/compact-cache-study.py`、`tools/verify/cache-large-output/compact-study.json`。

## 9. 超大原始数据读取与退出清理（1.0.17.6，2026-10-15）

用户提供的《故宫》压缩文件为 42,117,367 字节，扫描得到解压 NBT 为 3,119,088,997 字节。
旧路径在累计 547,377,063 字节时触及 512 MiB 配额，随后错误地把 GZIP 当作原始 NBT 再读，最终将真实超限掩盖为 `Unknown(31)`。

现在按文件头区分 GZIP 与原始 NBT。投影专用读取把 BlockStates 按 4096 个 long（32 KiB）分页：常量页只保留一个值，其余页使用 JDK Deflate level 1，压缩不划算则保留原页。
随机访问共用每线程最多 64 个解码页（2 MiB），页缓存键不反向持有整个投影。逻辑数据允许至 16 GiB，常驻数据另外限制为堆上限的三分之一、最多 1 GiB；普通 NBT 路径保留原配额。

真实读取结果：122 个区域、476,584,022 个非空气方块；BlockStates 逻辑为 3,111,813,120 字节，压缩页及索引约 62,957,376 字节（60.0 MiB）。这只是方块数据常驻量，不是整个应用的峰值内存。
实际 UI（资源已就绪）约 5.286 秒读取完成，约 37.675 秒总览就绪，然后取消后台工作并切换至水与活板门小投影成功。
这些测量未等待全部总览区块加载，也未等待《故宫》全部完整材质生成完成，不代表 4.77 亿方块场景的全覆盖或完整细节性能已验证。默认 256 MiB 预算对该文件的总览存在预算裁剪。

默认开启“关闭应用时清理渲染缓存”。退出时关闭模型读取、取消并等待引擎停止，再删除生成的场景和临时预览；关闭开关可跨启动复用缓存，配置单独保存。
清理路径固定在软件目录下的 cache/scenes 与 cache/previews，校验真实路径并拒绝链接；配置、资源包、导出文件和皮肤不参与清理。

验证包括：超过 512 MiB 的合成 NBT（压缩方块存储小于 2 MiB）、原始/GZIP 文件与流、原始损坏错误、负长度拒绝、随机词与跨页位索引精确一致；原有完整/分块几何、负坐标、重叠区域、LOD、PNG 与点选检查通过。
退出清理开关的实际界面测试覆盖设置保存、保留缓存、切换投影与构建中退出；清理器另验证重复清理、用户文件保留和链接拒绝。

最终打包版使用默认开启光照：约 5.390 秒读取完成，38.407 秒发布总览并确认首批区块可见；切换回小投影、重新开始大文件准备并关闭窗口，均通过。
引擎正常退出后清理场景及总览缓存；测试另核对配置和本地皮肤仍在，退出保留开关的单独测试也通过。

## 10. 完整区块按视角渐进发布（1.0.17.7，2026-10-15）

此前的分块解决了几何常驻内存，但完整文件结束前，前端无法读取已经生成的完整区块。
本轮在总览之后保留稳定光照和固定图集的准备阶段，随后按当前视角、视锥和漫游视距排序完整区块。
每个区块的四档页写好就发布描述和已提交长度；镜头改变后重排尚未生成的部分，生产队列最多提前两个区块。

前端同时持有总览和增长细节两个文件能力。增长文件的读取范围只随后端提交的长度增加，未发布范围、错误所有者、过期任务和第三个文件能力均拒绝。
每批最多接收 256 个区块描述，合并进原有显示实例；完整页上传成功后才替换对应总览。总览颜色不依赖完整图集的 UV，切换图集不会变成随机贴图。
全部完成后补齐标准 LMESH6 目录，通过硬链接（不支持时复制）发布不可变缓存；前端继续使用稳定的活跃路径，不重新打开文件、重读完整目录或清空已载入几何。

总览的颜色单元限制为 8 或 16 格，并使用稀疏占用记录；与 16 格所有权区块对齐，避免较大色块跨越独立替换区域。
特殊贴图注册阶段跳过普通方块组装、可见性编译与透明排序，之后正常完整区块构建保留原有算法。
后台自动刷新合并；用户镜头操作仍直接绘制。LOD 仅调整当前显示档位；关闭 LOD 后优先完整档，预算不足的区域保留可用总览，不主动降为中间档。

## 11. 紧凑面、真实 32 格构建与光照（1.0.17.9，2026-10-15）

LMESH7 在原有独立页压缩之上增加 40 字节紧凑面。编码只接受可精确还原的轴对齐 1×1 面，保存局部坐标、固定轴、顶点排列、UV 和颜色；复杂、倾斜、内缩几何与透明 BSP 使用原 80 字节通用路径。前端在显卡上传前展开为统一顶点格式，格式回归覆盖压缩/未压缩页、非法轴、CRC、异步取消和复杂几何回退。合成稠密场景文件为 997,083 字节；该结果受样例与压缩共同影响，不直接与旧样例文件作压缩率承诺。

32 格路径采用真实 2×2×2 批次组装，结果再按 16 格所有权分区，因此显示、视锥、连通性剔除和替换粒度保持不变。320×16×16 稠密样例四轮交错运行中，16 格与 32 格输出均为 20 个区块、245,760 面，中位耗时为 **225 ms** 与 **250 ms**，32 格约为 0.90×。普通交界、负坐标及重叠区域输出相同。结论是保留已验证的 32 格实验路径，但发布默认仍使用更快的 16 格构建。

全局光照把天空光和方块光源的两次全体扫描合为一次；无发光方块时跳过空的方块光传播，较大体积中用两个线程传播相互独立的通道。三类队列原型样例为 1.37×、1.24×、2.04×；生产传播在含屋顶与灯的样例为约 1.40×，开放天空与较小样例接近持平。稠密、紧凑和稀疏实现仍在 78,540 个格子上逐格一致。

NBT 回归另外覆盖低压缩率随机页的逻辑/常驻计数、生产常驻边界和 16 GiB 逻辑上限，不再依赖把生产限制临时放大。GIF 回归检查 GIF89a 文件头、精确帧数和一周旋转产生的可见帧差异；界面保存入口独立使用 GIF 筛选与扩展名。
